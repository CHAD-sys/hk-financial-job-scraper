How email actually works here

Two independent senders, one shared transport, and one configuration step that only ever ran for half of them. This is the whole path — from the moment something wants to send, to the moment Gmail accepts it.

28 July 2026 Transport: Gmail SMTP, port 587 Senders: 2
01

There are two email systems, not one

This is the single most important thing to hold in your head. They share credentials and a transport, and nothing else — different code, different triggers, different processes, different failure modes. When email "doesn't work", the first question is always which one.

Sender A · the scraper

The nightly brief

hk_jobs/notifications.py
  1. Cron runs scripts/daily_run.sh at about 02:00 HKT.
  2. Line 26 sources the secrets: source config/api_keys.env. Every later phase inherits them.
  3. Phases 1–6 scrape, fetch descriptions, enrich, sync PocketBase, poll LinkedIn, back up the database.
  4. Phase 7 runs pipeline --notify-summary, which calls send_daily_summary().
  5. It queries the database and diffs today against the most recent backup snapshot to get real new/closed counts.
  6. It builds two bodies — HTML and plain text — and hands them to _send_email().

Plus failure alerts: if any phase raises, pipeline.py catches it and fires send_failure_alert() immediately, with the phase name and how long it ran before dying.

Sender B · the website

Form submissions

webapp/backend/mailer.py
  1. A visitor submits the consultation form on / or the role form on /post-a-role.
  2. FastAPI validates the payload — field lengths, the career-stage enum, a real email address, an http(s) apply URL.
  3. The honeypot is checked. If filled, the request returns a normal 200 and stops here. Nothing is queued, nothing is sent.
  4. Rate limit by IP, per endpoint. Over the cap returns 429.
  5. It writes to disk first — an append-only line in data/enquiries.jsonl or submitted_roles.jsonl.
  6. Then it emails via send_mail(). Best-effort, by design — see §4.

Runs in the uvicorn process, which is a completely separate program from the scraper and shares none of its environment.

Shared by both · the transport

Both end at the same place: an authenticated SMTP session to Gmail. Same four steps, same credentials, same 587/STARTTLS handshake. 

# the handshake, identical in both senders
smtplib.SMTP("smtp.gmail.com", 587)   # open
  .starttls()                          # upgrade the plaintext socket to TLS
  .login(SMTP_USER, SMTP_PASS)         # Gmail App Password, never the account password
  .send_message(msg)                   # hand over the envelope
Why port 587 and not 465

587 opens in the clear and then upgrades to TLS with STARTTLS; 465 is TLS from the first byte. Both are fine, but they are not interchangeable — pointing 587's code at 465 hangs until the timeout, because the server is waiting for a TLS handshake while the client waits for a greeting. If you ever change SMTP_PORT, the connection method has to change with it.

02

Where the credentials come from

Four environment variables drive everything. Both senders read them the same way — os.getenv at import time — but they get them by completely different routes, and that difference is what broke.

VariableDefaultWhat it is
SMTP_HOSTsmtp.gmail.comMail server. Rarely changed.
SMTP_PORT587STARTTLS submission port.
SMTP_USER—The Gmail address sending the mail. Also the From header.
SMTP_PASS—A 16-character Gmail App Password, not the account password. Requires 2-Step Verification on the account.
NOTIFY_EMAILyour GmailWhere the scraper's brief and alerts go.
ENQUIRY_EMAILyour GmailWhere web enquiries go. A module constant — never read from a request.

Resolution order

Highest wins. This ordering is deliberate: the platform must always be able to override a file that happens to be lying around on disk.

1 · highest
The real process environment. On Railway, variables set in the dashboard. Nothing may overwrite these.
2
config/api_keys.env, loaded by env_file.py with override=False — it fills gaps and never clobbers. In production this file does not exist, and that is a no-op, not an error.
3 · lowest
Hardcoded defaults in the source. Host and port only. There is deliberately no default password.
The bug you hit, exactly

daily_run.sh line 26 runs source config/api_keys.env, so every scraper phase inherits the credentials. That is why the nightly brief has always worked.

The web backend is started by uvicorn main:app. There was no equivalent step, so it came up with a completely bare environment. mailer.py read SMTP_USER, got "", logged a warning, and returned False — while the endpoint still returned 200 OK because the submission had already been safely written to disk. Same credentials, same file, same machine. One process could see them and the other could not.

env_file.py now does for the backend what source does for the scraper.

03

What each message actually looks like

MessageTriggerFormatContains
Daily market brief Phase 7, nightly HTML + text
(multipart/alternative)		 Health status, live and unduplicated role counts, real new/closed delta against the previous backup, sample new roles, coverage, hidden-market count, vendor spend against the $30 cap.
Failure alert Any pipeline exception HTML + text Which phase died, the exception text, jobs collected before it died, and how long it ran.
Consultation enquiry Form on / plain text Name, email, career stage, message. Reply-To is set to the enquirer, so hitting reply just works.
Role submission Form on /post-a-role plain text Title, company, location, type, salary range, apply URL, submitter, full description.

The two senders build their messages differently and that is worth knowing if you ever edit one. The scraper uses MIMEMultipart("alternative") with a text part and an HTML part attached in that order — mail clients show the last part they understand, so HTML wins where supported and text is the fallback. The backend uses the newer EmailMessage API with a single plain-text body, because an enquiry has nothing to gain from markup.

04

Why a failed email never loses a submission

The ordering in the web endpoints is deliberate and it is the reason your "picolo" test was still recoverable after a day of no email. 

# webapp/backend/main.py — the order matters
stored = _persist("enquiries", data)   # 1. durable, append-only, on disk
sent   = send_mail(subject, body)     # 2. best-effort, may fail

if not stored and not sent:            # only a 500 if BOTH failed
    raise HTTPException(500, ...)

Disk first, mail second. If Gmail is down, if the app password is rotated, if the network drops — the submission is already on disk and the visitor still gets a success response, because from their side nothing went wrong. Only a double failure, where we could neither store nor send, is worth telling them about.

This is why nothing was lost

Every enquiry submitted during the broken period is sitting in data/enquiries.jsonl, one JSON object per line, with a received_at timestamp. The queue is the source of truth; the email is a notification about it. Read the file any time with:

cat data/enquiries.jsonl | python3 -m json.tool

Role submissions work the same way, with one addition: each is stored with status: "pending" and never reaches the public board until a human approves it through scripts/review_submissions.py.

05

The guardrails, and what each one stops

A public endpoint that sends mail is an open relay unless you are careful. Every one of these exists to stop a specific attack.

GuardrailStops
Recipient is a module constant
never read from the request		 Anyone POSTing a to field and using your Gmail to mail strangers. The recipient is fixed in code; a to in the payload is simply ignored.
CRLF stripped from every header
_header_safe()		 Header injection. A name like Jane\r\nBcc: victim@… would otherwise append a real Bcc header and turn the form into a spam cannon. There is a test that drives the real mailer and asserts no Bcc exists.
Off-screen honeypot field Naive bots. Positioned off-screen rather than display:none, because some bots skip hidden inputs but fill positioned ones. A filled honeypot gets a normal 200 and sends nothing — telling it that it was caught only helps it adapt.
Per-IP, per-endpoint rate limit Flooding your inbox and burning Gmail's sending quota. Uses the left-most X-Forwarded-For entry behind a proxy.
Hard length caps and enum validation A 10MB "message". Rejected outright rather than truncated, so nothing is silently mangled.
App Password, not the account password Full account compromise if the environment leaks. An App Password is scoped to SMTP and revocable on its own without touching the account.
06

When mail stops: a runbook

The failure that just happened was invisible for a day because success was never logged and only warnings surfaced. All three of those gaps are now closed. Here is how to diagnose in order of cheapness.

Step 1 — ask the server whether it is even configured

curl -s localhost:8000/health | python3 -m json.tool

{ "status": "ok",
  "email": "configured",                ← what you want
  "enquiry_recipient": "you@gmail.com" }

{ "email": "NOT CONFIGURED — enquiries queue but no mail is sent" }
                                        ← credentials missing

This works in production without shell access, which is the point.

Step 2 — read the boot lines

healthy startup looks like this:
INFO env_file: Loaded 6 setting(s) from api_keys.env: …, SMTP_PASS, SMTP_USER
INFO main:     Email configured — enquiries will be sent to you@gmail.com

and after a submission:
INFO mailer:   Sent 'Consultation enquiry — …' to you@gmail.com

Successes are logged now, not just failures. "No error in the log" was never good evidence that mail was flowing.

Step 3 — match the symptom

SymptomMost likely causeFix
Form says success, no email, queue file has the entry config Credentials not visible to the process Check /health. Locally, confirm config/api_keys.env exists. In production, set the variables in the platform.
Form errors with 500 disk Could not write the queue and could not send Check the submissions directory exists and is writable.
535 Username and Password not accepted auth Regular password used, or App Password revoked Regenerate a 16-character App Password. 2-Step Verification must be on.
Connection hangs, then times out port Port/method mismatch, or egress blocked 587 with STARTTLS. Some hosts block outbound 25/465/587 — check the platform's egress rules.
Nightly brief arrives, web enquiries do not split Classic two-system split The scraper is fine; the backend is missing config. Exactly the bug in §2.
Nothing arrives from either sender upstream Account-level: quota, suspension, revoked password Send a test directly through mailer.send_mail to isolate transport from application.
Form says success, queue file is empty bot The honeypot fired Working as designed. Grep the log for Honeypot triggered.

Step 4 — isolate transport from application

# bypasses FastAPI entirely; proves the credentials and the network
set -a; . ./config/api_keys.env; set +a
cd webapp/backend && python -c "import mailer; print(mailer.send_mail('test','hello'))"

True   → transport is fine, the problem is in the app
False  → credentials, network or Gmail itself
07

Before this works in production

Everything above is verified on localhost. Production is a different environment and config/api_keys.env does not exist there.

Required
Set SMTP_USER and SMTP_PASS in the platform environment. Without them the site still accepts enquiries and still queues them — it just never tells you they arrived.
Required
Set CORS_ORIGINS to the real frontend domain. This is not an email setting, but it fails first: the browser blocks the request before it ever reaches the endpoint, so no email is even attempted.
Required
Set SUBMISSIONS_DIR to a persistent volume. The queue is the durability guarantee. On ephemeral container storage it is erased on every deploy, and the guarantee quietly becomes false.
Recommended
Move off the personal Gmail. It is one account behind a public endpoint, with a personal address as the visible From. Gmail's limit is roughly 500 messages a day and abuse can lock the whole account — including your own mail. A dedicated address, or a transactional provider, before this carries real volume.
Verify
Submit a real enquiry through the deployed site and confirm both the log line and the inbox. Do not assume it works because it worked locally — CORS and egress rules are exactly the things that differ.
Source of truth for everything above: hk_jobs/notifications.py and scripts/daily_run.sh for the scraper; webapp/backend/mailer.py, env_file.py and main.py for the website. Behaviour described here is covered by tests/test_env_file.py and tests/test_submit_endpoints.py — including that a header-injection attempt never produces a Bcc, and that an existing environment variable always beats the file on disk.
